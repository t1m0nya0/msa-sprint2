# ADR-001: Поэтапная миграция Hotelio на микросервисную архитектуру

**Статус:** Принято  
**Дата:** 2026-05-19  
**Автор:** Nurbulatuly Tamirlan  
**GitHub:** https://github.com/t1m0nya0/msa-sprint2

## Контекст

Hotelio — платформа бронирования отелей на Java Spring Boot монолите с единой PostgreSQL. С ростом нагрузки и команды возникли проблемы:

- **Сопровождение:** любое изменение требует понимания всей кодовой базы; модули тесно связаны.
- **Масштабирование:** нельзя масштабировать только `BookingService` при пиках бронирований.
- **CI/CD:** единый деплой монолита замедляет релизы и повышает риск регрессий.
- **Frontend:** универсальный REST не покрывает потребности разных клиентов; нет BFF/GraphQL.
- **Аналитика:** прямой доступ к боевой БД для статистики недопустим.

Дополнительно при анализе кода выявлено:

- `BookingService` вызывает 4 других сервиса синхронно — это критический hub coupling.
- Все домены используют одну БД — schema coupling и сложность разделения.
- Создание бронирования — самый нагруженный и бизнес-критичный сценарий.

## Решение

Применить паттерн **Strangler Fig** с поэтапным выносом доменов. Первым выносим **BookingService**, так как:

1. Наибольшая нагрузка и бизнес-ценность.
2. Явные зависимости от других модулей — их можно временно получать через REST монолита (Anti-Corruption Layer).
3. Асинхронная статистика через Kafka не нагружает боевую БД.
4. Команда из 2 Java-разработчиков может параллельно работать над новым сервисом, не блокируя монолит.

### Целевое состояние (To-Be, ~2 месяца)

- `booking-service` — gRPC, отдельная БД, события в Kafka.
- `booking-history-service` — read-модель для аналитики.
- Монолит — прокси для create booking, остальные домены без изменений.
- GraphQL Federation (BFF) для личного кабинета.
- CI/CD + Helm + Kubernetes для новых серvice.
- Istio Service Mesh для canary и circuit breaking.

### Альтернативы

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| Big Bang rewrite | Чистая архитектура | Высокий риск, долго, нет ресурсов |
| Modular monolith | Меньше инфраструктуры | Не решает масштабирование booking |
| **Strangler Fig (выбрано)** | Постепенно, низкий риск | Временная сложность dual-write/proxy |

## План миграции (Strangler Fig)

### Фаза 1 — Booking (текущий спринт)
1. Развернуть `booking-service` + отдельная БД.
2. Прокси в монолите: `POST /api/bookings` → gRPC.
3. `GET /api/bookings` остаётся в монолите (legacy read path).
4. Kafka → `booking-history-service`.

### Фаза 2 — Read path
1. Перенести `GET /api/bookings` в микросервис.
2. Синхронизация исторических данных (CDC или batch migration).

### Фаза 3 — Hotel + User
1. Выделить `hotel-service`, `user-service`.
2. Убрать REST-зависимости booking → monolith.

### Фаза 4 — GraphQL + Gateway
1. Apollo Federation как единая точка для фронтенда.
2. ACL на уровне полей.

### Фаза 5 — Service Mesh
1. Istio: canary 90/10, circuit breaker, feature flags через Envoy.

## Последствия

**Плюсы:** независимое масштабирование booking, асинхронная аналитика, основа для CI/CD и mesh.

**Минусы:** временная dual-database модель, операционная сложность (Kafka, K8s, Istio).

**Риски:** рассинхрон данных между монолитом и booking-service — mitigated через event sourcing в Kafka.
